# ТЗ: авто-ротация wallpaper из Google Drive (iOS)

## Контекст
- Платформа: iPhone (допущение, не подтверждено явно).
- Цель: lock screen ротирует фото, при этом источником правды остаётся папка в Google Drive — пользователь кидает/удаляет файлы там, а не в Photos.
- Бюджет: разовая покупка допустима (в т.ч. платно), подписки исключены.
- Готовые приложения под весь сценарий целиком не найдены (см. "Рассмотренные готовые решения").

## Архитектура: два независимых компонента

Вместо одного приложения, которое одновременно тянет фото из Drive и программно меняет wallpaper, — два развязанных куска:

### Компонент A — Sync-агент (Drive → Photos, одностороннее зеркало)
- Единственная задача: держать один выделенный альбом в Photos синхронизированным с папкой в Google Drive.
- Drive — источник правды. Альбом в Photos — производный, доступен только на чтение для пользователя (руками туда не лезем).
- Логика: файл появился в Drive → добавить в альбом. Файл удалён из Drive → удалить соответствующий asset из альбома.
- Технически: Google Drive API (OAuth) для чтения списка файлов + `PHPhotoLibrary` (публичный API добавления/удаления ассетов из альбома, App Store-safe, без джейлбрейка и без приватных вызовов).
- Кроп/resize — вне MVP, см. "Backlog / не в MVP".

### Компонент B — Ротация (нативный iOS Photo Shuffle)
- С iOS 17.1 Photo Shuffle умеет брать источником конкретный альбом (не только смарт-категории Apple) и настраивать частоту: On Tap / On Lock / Hourly / Daily.
- Это закрывает всю задачу "ротация wallpaper по расписанию" средствами самой ОС — без единой строчки кода и без приватных API.
- Настраивается пользователем один раз вручную: Lock Screen → Photo Shuffle → выбрать альбом, синхронизируемый компонентом A.

Ключевой эффект такого разделения: **приложению больше не нужен приватный wallpaper API** (которого не существует для сторонних разработчиков на не-джейлбрейкнутом iOS — см. предыдущее ревью). Sync-агент работает только с Photos и Drive, оба — публичные, поддерживаемые API.

## Требования к sync-агенту

### 1. Источник и авторизация
- Папка в Google Drive пользователя, любые пропорции/размеры файлов.
- OAuth: `GoogleSignIn-iOS` SDK (официальный, PKCE/keychain/refresh — внутри), scope `drive.readonly`.
- Выбор папки — нативный SwiftUI-браузер по Drive API (`files.list` с `q='<id>' in parents`), а не Google Picker: у Picker нет нативного iOS SDK, это JS-виджет для веба, интеграция потребовала бы WKWebView с мостом на native — сложность не оправдана для личного инструмента.
- Компромисс: `drive.readonly` — "restricted" scope, для долгоживущих токенов (без ре-логина каждые 7 дней) приложение нужно перевести из Testing в Published в Google Cloud Console. Т.к. scope restricted, это не проходит совсем без предупреждений: пользователь при входе увидит экран "Google hasn't verified this app" и должен один раз кликнуть через Advanced → Go to app. Для личного использования (один аккаунт, сам разработчик) это стандартная практика у хобби-проектов; риск — Google теоретически может ограничить/отозвать доступ у неверифицированного restricted-scope клиента, но при малом числе пользователей это на практике не наблюдается.

### 2. Синхронизация
- Односторонняя: Drive → альбом Photos.
- Добавление новых файлов и удаление тех, что пропали из Drive-папки.
- Сопоставление "файл в Drive" ↔ "asset в Photos" (дефолтный вариант, стандартный паттерн для one-way mirror-инструментов):
  - Ключ — стабильный Drive `file.id` (не имя файла: имя может меняться при переименовании в Drive, а `file.id` — нет).
  - Локальная mapping-таблица `driveFileId → PHAsset.localIdentifier`, персистится на устройстве (простой JSON/plist в песочнице приложения — для личной коллекции фото полноценная БД избыточна).
  - На каждом прогоне синка: сравнить текущий список файлов в Drive-папке с ключами mapping-таблицы → новые id = добавить в альбом и записать в таблицу; пропавшие id = удалить asset из альбома и убрать из таблицы.
  - Опционально на будущее: Drive отдаёт `modifiedTime`/`md5Checksum` для каждого файла — можно хранить и их в mapping-таблице, чтобы отличать "файл изменился по содержимому" от "файл не менялся", и обновлять asset при изменении. Не обязательно для MVP (простое добавление/удаление уже покрывает основной сценарий).
  - Риск: если приложение удалить и переустановить, mapping-таблица потеряется, и следующий синк не будет знать, что уже есть в альбоме, дублирует запросы. Смягчение — не в MVP.

### 4. Триггер синхронизации
- Не обязана быть real-time — если Drive обновился, а альбом подхватил изменения через час-два, это не проблема (в отличие от предыдущей схемы, где от частоты зависела сама ротация).
- На iOS фоновые задачи выполняются через `BGTaskScheduler` — публичный API, но без гарантии точного интервала (ОС сама решает, когда дать время). Приемлемо для этой задачи.

### 5. Дистрибуция / подпись (ограничение iOS)
- Без App Store, без платного Apple Developer Program ($99/год).
- Sideload через AltStore Classic:
  - AltServer на Windows-компьютере пользователя (комп работает почти каждый день → авто-рефреш подписи раз в ~7 дней решается сам собой).
  - На телефон — именно AltStore (не разовый sideload IPA), чтобы приложение само пере-подписывалось при обнаружении AltServer в локальной сети.
  - Альтернатива на будущее: SideStore (разовая настройка pairing file + WireGuard-туннель, дальше пере-подпись по воздуху без компа).
- Т.к. агент использует только публичные API, теоретически годится и для нормальной публикации через App Store/TestFlight — но это отдельное решение, не обязательное для MVP.

## Рассмотренные готовые решения (не найдено подходящего)
- Существующие iOS-приложения для синка Google Drive ↔ Photos работают в обратную сторону (Photos → Drive, бэкап), а не Drive → Photos.
- Найденные приложения такого рода — подписочные (например "Sync with Google Drive" — free-тариф ограничен 3 папками/200 фото, remove-ограничений только по подписке).
- Готового направления "Drive-папка как источник правды → зеркалируемый альбом Photos с удалениями" не нашлось ни в бесплатном, ни в разовой покупке виде — писать самим.

## Открытые вопросы (не решены в этой сессии)
- Раздельные lock screen / home screen альбомы или общий.

## Backlog / не в MVP
- Precise crop: aspect-fill + center-crop под физическое разрешение экрана перед вставкой в альбом. Отложено сознательно — MVP отдаёт кадрирование целиком нативному Photo Shuffle (subject-aware zoom), точного контроля над кропом нет. Вернуться к этому, если нативное поведение не устроит по факту использования.
- Отслеживание изменения содержимого файла при том же `file.id` (через `modifiedTime`/`md5Checksum`) — MVP синхронизирует только добавление/удаление.

## Из отклонённых вариантов (для контекста, не делать)
- Одно приложение, которое само программно меняет wallpaper в фоне — отклонено: на iOS нет публичного API для установки wallpaper сторонним приложением; приватный API работает только на джейлбрейке.
- Платный Apple Developer Program — отклонён из-за бюджетных условий.
